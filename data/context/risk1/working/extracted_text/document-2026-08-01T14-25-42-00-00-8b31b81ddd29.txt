## Lectura funcional del modelo semantico

El modelo semantico `Modelo_semantico_riesgos` es la capa de consumo de Power BI sobre las salidas Gold de riesgo. No recalcula el modelo funcional desde cero: recibe resultados ya calculados en Gold y los organiza para analisis, filtros, explicabilidad y futuras lecturas asistidas por agentes.

La idea central es separar tres preguntas distintas:

1. cual es el riesgo final de una entidad;
2. que bloques explican ese resultado;
3. que reglas concretas aportan a cada bloque.

Por eso el modelo conserva hechos a tres niveles:

- nivel final: `fact_riesgo_*`;
- nivel bloque: `fact_impacto_bloque_*` y `fact_probabilidad_bloque_*`;
- nivel regla: `fact_impacto_*` y `fact_probabilidad_*`, cuando el dominio lo publica.

El riesgo final no debe recalcularse en el reporte. La combinacion entre probabilidad e impacto ya llega desde Gold mediante la matriz 4 x 4 publicada en `silver.ref_risk_final_matrix`. En Power BI se debe leer `riesgo_final_num` y `riesgo_final_texto` como resultado final del calculo.

## Dimensiones compartidas

Estas dimensiones son la base para construir paginas consistentes:

| Dimension | Uso recomendado | Observaciones |
| --- | --- | --- |
| `dim_run_modelo` | fijar el snapshot visible del modelo | usar `fecha_carga` para mostrar la fecha; `run_id` queda como clave tecnica |
| `dim_departamento_master` | slicer transversal de departamento | filtra SIC, INFRA, CULTURA, GOVERNANCA y LLDT a traves de sus dimensiones nativas |
| `dim_riesgo_master` | filtro o agrupacion transversal de riesgo | usa `risk_key = DOMINIO|id_risc` para no mezclar ids iguales de dominios distintos |
| `dim_amenaza_master` | analisis transversal de amenazas | aplica a SIC e INFRA; CULTURA, GOVERNANCA y LLDT no tienen superficie comun de amenazas |

Tambien existen dimensiones especificas por dominio. Se usan cuando la pagina baja al detalle nativo del eje:

- aplicaciones: `dim_aplicacion_sic`, `dim_aplicacion_infra`;
- departamentos de referencia con atributos auxiliares de SIC: `dim_aplicacion_cultura`, `dim_aplicacion_governanca`;
- departamentos LLDT: `dim_departamento_pt`;
- reglas: `dim_regla_sic`, `dim_regla_infra`, `dim_regla_pt`, `dim_regla_cultura`, `dim_regla_governanca`;
- supuestos: `dim_supuesto_modelo_sic`, `dim_supuesto_modelo_infra`, `dim_supuesto_modelo_pt`, `dim_supuesto_modelo_cultura`, `dim_supuesto_modelo_governanca`.

Nota practica:

- en SIC, `dim_aplicacion_sic[nombre_extendido]` es la etiqueta visible recomendada para slicers, combos y filas de matrices cuando se quiera ver `sic + nombre` en una sola columna.

## Claves y relaciones que conviene respetar

El modelo publica varias claves para evitar ambiguedades:

| Clave | Significado | Uso |
| --- | --- | --- |
| `run_id` | identificador tecnico de la ejecucion Gold | relaciona facts con `dim_run_modelo`; no exponer como slicer funcional |
| `sic` | identificador de aplicacion o activo en ejes aplicacionales | en SIC e INFRA es clave nativa; en CULTURA y GOVERNANCA queda como atributo auxiliar |
| `codigo_departamento` | codigo departamental normalizado | une LLDT y dimensiones aplicacionales con `dim_departamento_master` |
| `codigo_departamento_ref` | codigo departamental de referencia para CULTURA y GOVERNANCA | clave de navegacion y filtrado de esos dos dominios |
| `id_risc` | id de riesgo dentro de un dominio | valido para detalle dentro del eje, no para comparar dominios sin prefijo |
| `risk_key` | clave tecnica `DOMINIO|id_risc` | clave recomendada para filtros transversales con `dim_riesgo_master` |
| `id_amenaca` | id de amenaza dentro de SIC o INFRA | usar dentro del dominio |
| `amenaza_key` | clave tecnica `DOMINIO|id_amenaca` | clave recomendada para `dim_amenaza_master` |
| `codigo_regla` | clave funcional de regla | une facts de detalle con `dim_regla_*` y supuestos |

Regla practica: para analisis dentro de un eje se puede usar el id nativo; para analisis entre ejes usar siempre la clave con prefijo (`risk_key` o `amenaza_key`).

## Que tabla usar segun la pregunta

| Pregunta | Tabla principal | Dimensiones de apoyo | Notas |
| --- | --- | --- | --- |
| Riesgo final por activo, SIC o departamento | `fact_riesgo_*` | `dim_run_modelo`, `dim_riesgo_master`, dimension de entidad | usar `riesgo_final_texto` / `riesgo_final_num` |
| Distribucion por severidad | `fact_riesgo_*` | `dim_riesgo_master`, `dim_departamento_master` | contar entidades, no sumar nivel numerico |
| Por que salio esa probabilidad | `fact_probabilidad_*` | `dim_regla_*`, `dim_supuesto_modelo_*` | nivel de regla; usar `regla_nombre` y `regla_descripcion` |
| Por que salio ese impacto | `fact_impacto_*` | `dim_regla_*`, `dim_supuesto_modelo_*` | aplica a SIC, INFRA, CULTURA y GOVERNANCA; LLDT publica impacto a nivel bloque |
| Resumen de probabilidad por bloque | `fact_probabilidad_bloque_*` | `dim_riesgo_master` | explica agregacion de reglas de probabilidad |
| Resumen de impacto por bloque | `fact_impacto_bloque_*` | `dim_riesgo_master` | explica agregacion de reglas o fuente de impacto |
| Amenazas asociadas a riesgos | `bridge_riesgo_amenaza_sic` o `bridge_riesgo_amenaza_infra` | `dim_amenaza_master`, `dim_riesgo_master` | solo SIC e INFRA |
| Calidad de calculo, proxies y defaults | facts de bloque y `dim_supuesto_modelo_*` | `dim_regla_*` | revisar `reales`, `proxies`, `defaults_cnt`, `constantes`, `pendientes`, `no_disponibles` |

## Contrato comun de reglas

Las cinco tablas de reglas tienen el mismo contrato minimo visible:

| Campo | Significado | Uso BI |
| --- | --- | --- |
| `codigo_regla` | clave funcional de la regla | relacion y detalle tecnico-funcional |
| `regla_nombre` | nombre corto visible | filas de matriz, titulos y tooltips cortos |
| `regla_descripcion` | descripcion funcional larga | tooltips, paginas de detalle y explicabilidad |
| `bloque` | bloque de calculo | agrupar reglas por probabilidad o impacto |
| `id_risc` / `risc` | riesgo funcional asociado | explicar que riesgo mide la regla |
| `activa` | vigencia de la regla | filtrar catalogos o validar backlog funcional |

La regla recomendada en Power BI es mostrar `regla_nombre` como etiqueta principal y `regla_descripcion` como descripcion extendida. `codigo_regla` debe quedar visible cuando el usuario necesite trazabilidad o conciliacion con Gold.

## Detalle por eje

### SIC

SIC representa el eje de aplicaciones y sistemas con el detalle funcional mas completo. Su entidad principal es la aplicacion identificada por `sic`.

Tablas principales:

| Tipo | Tabla | Uso |
| --- | --- | --- |
| entidad | `dim_aplicacion_sic` | atributos de aplicacion, departamento, CIDAT, RTO/RPO, criticidad, ENS y etiqueta visible `nombre_extendido` |
| riesgo final | `fact_riesgo_sic` | salida final por `sic`, bloque y riesgo |
| probabilidad regla | `fact_probabilidad_sic` | detalle por `sic`, `codigo_regla` y riesgo, con `usa_default` y `peso_regla` |
| impacto regla | `fact_impacto_sic` | detalle por `sic`, `codigo_regla` y riesgo, con `usa_default` y `peso_regla` |
| probabilidad bloque | `fact_probabilidad_bloque_sic` | promedio y cobertura de reglas de probabilidad por bloque |
| impacto bloque | `fact_impacto_bloque_sic` | promedio y cobertura de reglas de impacto por bloque |
| resumen activo | `fact_probabilidad_sig_sic`, `fact_impacto_sig_sic` | lectura agregada por SIC sin bajar al riesgo |
| reglas | `dim_regla_sic` | catalogo funcional con nombre, descripcion larga, pesos y metadata de default |
| amenazas | `dim_amenaza_master`, `dim_amenaza_filtro_sic`, `bridge_riesgo_amenaza_sic` | analisis riesgo-amenaza |

Nota de consumo:

- `fact_probabilidad_sic` y `fact_impacto_sic` solo quedan en una fila por regla cuando el analisis esta acotado a un SIC concreto y a una sola ejecucion visible. Si se consulta solo `codigo_regla` fuera de ese contexto, la repeticion de filas responde al grano natural `sic + regla + riesgo + run_id`.

Consultas recomendadas:

- pagina ejecutiva SIC: empezar en `fact_riesgo_sic`, contar `sic` y agrupar por `riesgo_final_texto`, `risc`, departamento o aplicacion;
- detalle de reglas SIC: usar `fact_probabilidad_sic` y `fact_impacto_sic` con `dim_regla_sic`, mostrando `tipo_valor`, `usa_default`, `peso_regla` y, si hace falta, `default_nivel_num` / `default_nivel_texto`;
- amenazas SIC: usar `bridge_riesgo_amenaza_sic` con `dim_amenaza_master` y filtrar los facts por `risk_key`;
- ficha de aplicacion: combinar `dim_aplicacion_sic` con `fact_riesgo_sic`, preferir `nombre_extendido` como etiqueta visible, y agregar detalle de reglas solo como tablas separadas.

No recomendado:

- sumar `riesgo_final_num`, `impacto_final_num` o `probabilidad_final_num` como metrica principal;
- mezclar `id_risc` de SIC con otros dominios sin usar `risk_key`.

INFRA es un eje aplicacional equivalente a SIC en estructura semantica, pero con scope propio desde `silver.dim_infra_cidat`. La entidad principal tambien se expone como `sic` por compatibilidad del contrato, aunque funcionalmente representa activo INFRA.

Tablas principales:

| Tipo | Tabla | Uso |
| --- | --- | --- |
| entidad | `dim_aplicacion_infra` | atributos del activo INFRA, departamento, CIDAT, RTO/RPO y criticidad |
| riesgo final | `fact_riesgo_infra` | salida final por activo, bloque y riesgo |
| probabilidad regla | `fact_probabilidad_infra` | detalle de reglas de probabilidad, con `usa_default` y `peso_regla` |
| impacto regla | `fact_impacto_infra` | detalle de reglas de impacto, con `usa_default` y `peso_regla` |
| bloque | `fact_probabilidad_bloque_infra`, `fact_impacto_bloque_infra` | lectura de agregacion por bloque |
| resumen activo | `fact_probabilidad_sig_infra`, `fact_impacto_sig_infra` | lectura agregada por activo INFRA |
| reglas | `dim_regla_infra` | contrato comun con nombre, descripcion larga, pesos y metadata de default |
| amenazas | `dim_amenaza_master`, `dim_amenaza_filtro_infra`, `bridge_riesgo_amenaza_infra` | analisis riesgo-amenaza INFRA |

Consultas recomendadas:

- resumen INFRA: `fact_riesgo_infra` con `dim_aplicacion_infra` y `dim_riesgo_master` filtrando dominio INFRA;
- comparacion con SIC: usar medidas separadas por eje o visuales separados, no una unica cuenta mezclada sin dominio;
- explicacion de reglas: `fact_probabilidad_infra` / `fact_impacto_infra` con `dim_regla_infra`, mostrando `tipo_valor`, `usa_default`, `peso_regla` y `default_nivel_num` / `default_nivel_texto` cuando aplique.

### LLDT

LLDT representa riesgo de puestos de trabajo o ambito departamental. Su entidad principal es el departamento o scope funcional, no la aplicacion.

Tablas principales:

| Tipo | Tabla | Uso |
| --- | --- | --- |
| entidad | `dim_departamento_pt` | detalle nativo del departamento LLDT |
| riesgo final | `fact_riesgo_pt` | salida final por departamento y riesgo |
| probabilidad regla | `fact_probabilidad_pt` | detalle por regla de probabilidad, con `usa_default` y `peso_regla` en el ultimo nivel |
| probabilidad bloque | `fact_probabilidad_bloque_pt` | agregacion de probabilidad por bloque y riesgo |
| impacto bloque | `fact_impacto_bloque_pt` | impacto final del bloque LLDT |
| reglas | `dim_regla_pt` | reglas LLDT con nombre, descripcion larga, pesos y metadata de default |
| riesgos | `dim_riesgo_filtro_pt`, `dim_riesgo_master` | filtro nativo o transversal de riesgo |

Consultas recomendadas:

- detalle causal de probabilidad: `fact_probabilidad_pt` con `dim_regla_pt`, mostrando `tipo_valor`, `usa_default`, `peso_regla` y, si hace falta explicar configuracion, `default_nivel_num` / `default_nivel_texto` desde la dimension de regla;

- comparacion transversal de riesgos: usar `risk_key` contra `dim_riesgo_master`.

Nota: LLDT no tiene catalogo comun de amenazas. Las paginas de amenazas deben limitarse a SIC e INFRA.

### CULTURA

CULTURA reutiliza atributos del universo aplicacional de SIC, pero calcula un eje propio orientado a comportamiento, formacion y variables funcionales del dominio. Su entidad principal es el departamento de referencia publicado en `codigo_departamento_ref`; `sic` queda solo como atributo canonico auxiliar.

Tablas principales:

| Tipo | Tabla | Uso |
| --- | --- | --- |
| entidad | `dim_aplicacion_cultura` | scope a grano departamento con `codigo_departamento_ref`, `nombre_departamento_ref` y SIC canonico auxiliar |
| riesgo final | `fact_riesgo_cultura` | salida final por departamento, bloque y riesgo |
| probabilidad regla | `fact_probabilidad_cultura` | detalle por regla, pesos, defaults y fuente principal |
| impacto regla | `fact_impacto_cultura` | detalle de impacto por regla |
| bloque | `fact_probabilidad_bloque_cultura`, `fact_impacto_bloque_cultura` | agregacion por bloque |
| reglas | `dim_regla_cultura` | contrato comun de regla con descripcion larga |
| supuestos | `dim_supuesto_modelo_cultura` | proxies, defaults y decisiones funcionales |

Consultas recomendadas:

- resumen CULTURA: `fact_riesgo_cultura` con `dim_aplicacion_cultura` y `dim_departamento_master`;
- explicabilidad: `fact_probabilidad_cultura` y `fact_impacto_cultura` con `dim_regla_cultura`;
- gobierno de defaults: revisar `usa_default`, `tipo_valor`, `peso_regla`, `defaults_cnt` y `dim_supuesto_modelo_cultura`.

Regla practica:

- usar `sic` o `nom_app` solo como ayuda de trazabilidad y navegacion, no como unidad canonica del eje.

No usar CULTURA para analisis de amenazas; no publica bridge de amenazas como SIC o INFRA.

Consultas recomendadas:

Regla practica:

- para cards o volumetria usar conteo distinto de `codigo_departamento_ref`;

Igual que CULTURA, no debe usarse para paginas de amenazas porque no tiene bridge de amenaza compartido.

## Patrones de consulta en Power BI

### Conteos recomendados

Para paginas ejecutivas, la medida principal suele ser un conteo de entidades:

- SIC: distinct count de `fact_riesgo_sic[sic]` o medida `SICs` si aplica al visual;
- INFRA: distinct count de `fact_riesgo_infra[sic]` o medida `INFRAs` si aplica al visual;
- LLDT: distinct count de `fact_riesgo_pt[codigo_departamento]`;
- CULTURA: distinct count de `fact_riesgo_cultura[codigo_departamento_ref]`;
- GOVERNANCA: distinct count de `fact_riesgo_governanca[codigo_departamento_ref]`.

Para matrices por severidad, usar `riesgo_final_texto` como columna/fila de clasificacion y la entidad como conteo. El numero de severidad (`riesgo_final_num`) sirve para ordenar, no para sumar.

### Filtros recomendados

Filtros globales:

- `dim_run_modelo[fecha_carga]` como referencia temporal visible;
- `dim_departamento_master[nombre_departamento]` cuando la pagina compare dominios o necesite filtro transversal;
- `dim_riesgo_master[risc]` cuando la lectura sea por riesgo compartido, fijando o mostrando `dominio_modelo` si hay varios ejes.

Filtros por eje:

- SIC: `dim_aplicacion_sic[nombre_extendido]`, y dejar `dim_aplicacion_sic[sic]` como apoyo tecnico cuando haga falta, mas `dim_amenaza_master[amenaca_acc]`;
- INFRA: `dim_aplicacion_infra[sic]`, `dim_aplicacion_infra[nom_app]`, `dim_amenaza_master[amenaca_acc]`;
- LLDT: `dim_departamento_pt[nombre_departamento]` cuando la pagina sea solo LLDT;
- CULTURA: `dim_aplicacion_cultura[nombre_departamento_ref]`, `dim_aplicacion_cultura[codigo_departamento_ref]` y, solo si hace falta trazabilidad, `dim_aplicacion_cultura[sic]` o `dim_aplicacion_cultura[nom_app]`;
- GOVERNANCA: `dim_aplicacion_governanca[nombre_departamento_ref]`, `dim_aplicacion_governanca[codigo_departamento_ref]` y, solo si hace falta trazabilidad, `dim_aplicacion_governanca[sic]` o `dim_aplicacion_governanca[nom_app]`.

### Antipatrones a evitar

- sumar niveles numericos de riesgo, impacto o probabilidad;
- mezclar reglas de dominios distintos en una misma tabla sin mostrar `dominio_modelo`;
- usar `id_risc` como si fuera global;
- inferir la ejecucion vigente desde una fact en lugar de usar `dim_run_modelo`;
- usar `pres1.pbix` como fuente documental del reporte vigente;
- construir paginas de amenazas para CULTURA, GOVERNANCA o LLDT sin una fuente de amenazas publicada.

## Lineamientos para construir cualquier pagina analitica

## 1. Empezar por la pregunta analitica, no por el visual

Antes de diseñar una pagina, definir explicitamente:

- que dominio responde: `SIC`, `LLDT`, `CULTURA`, `GOVERNANCA`, `INFRA` o combinado;
- cual es el grano visible: SIC, departamento o riesgo;
- cual es la medida principal: conteo, distinct count o texto de clasificacion;
- que decision deberia habilitar la pagina.

Si la pagina no tiene una pregunta clara, termina mezclando granos y pierde valor.

## 2. Respetar el snapshot publicado

- La referencia temporal visible es `dim_run_modelo[fecha_carga]`.
- `run_id` se mantiene como clave tecnica, no como slicer visible.
- No inferir la ejecucion vigente mirando facts sueltas.

## 3. Usar la dimension correcta para cada lectura

- Riesgo descriptivo: `dim_riesgo_master`
- Departamento transversal: `dim_departamento_master`
- Amenazas SIC: `dim_amenaza_master`
- Detalle SIC: `dim_aplicacion_sic`
- Detalle LLDT: `dim_departamento_pt` solo cuando haga falta bajar al scope nativo LLDT
- Detalle INFRA: `dim_aplicacion_infra` y dimensiones de amenaza/riesgo INFRA cuando la lectura sea de infraestructura

## 4. No sumar valores que no son aditivos

No usar como agregacion principal:

- `riesgo_raw`
- `riesgo_final_num`
- `impacto_raw`
- `probabilidad_raw`

Nota funcional importante:

- `riesgo_final_num` ya llega calculado en Gold con la matriz 4x4 de doble entrada entre probabilidad e impacto;
- no debe reconstruirse en DAX como promedio, redondeo ni combinacion lineal de `probabilidad_final_num` e `impacto_final_num`.

Patron correcto:

- `DISTINCTCOUNT` de entidades visibles;
- medidas por severidad;
- clasificaciones textuales como salida visual;
- matrices reales para comparar riesgo x nivel.

## 5. Separar dominios cuando la lectura lo necesita

Si la pagina combina varios dominios:

- usar bloques separados por dominio;
- fijar `dim_riesgo_master[dominio_modelo]` en cada visual o pagina;
- no mezclar dominios en una misma matriz sin discriminacion clara.

Si la pagina es de un solo dominio, fijar el dominio y evitar ruido visual.

## 6. Priorizar matrices reales sobre composiciones fake

Cuando la pregunta es comparativa por riesgo y severidad, la pieza correcta es una matriz real.

No conviene simular una grilla con cards sueltas cuando el usuario necesita:

- comparar columnas;
- leer cruces fila x columna;
- ver rapidamente donde esta la concentracion.

## 7. Mantener filtros globales estables

Patron base recomendado para el reporte combinado:

1. `dim_departamento_master[nombre_departamento]`
2. `dim_run_modelo[fecha_carga]`

Patrones especificos por pagina:

- SIC detalle: riesgo, nivel final, SIC
- SIC amenazas: amenaza, departamento; riesgo y nivel final entran completos sin slicers expuestos, y las grillas se filtran con [Tiene SICs visibles] = 1 o [SICs] > 0
- SIC detalle maximo: fecha, departamento y SIC; dos grillas separadas para impacto y probabilidad por codigo de regla
- LLDT: preferir resumen por riesgo y severidad; para lectura causal usar reglas LLDT sobre `dim_regla_pt` y `fact_probabilidad_pt`

## 8. Hacer visible la severidad con un codigo visual consistente

Escala vigente sugerida:

- Bajo: verde suave
- Medio: arena
- Alto: naranja suave
- Muy alto: rojo o rosa suave

La misma escala deberia repetirse entre paginas para que el usuario no reaprenda el mapa cromatico.

## 9. No depender del PBIX minimo como flujo principal

El reporte operativo actual se administró en servicio y no debe documentarse como si dependiera de `pres1.pbix`.

Si hace falta editar en Desktop:

1. abrir `semantic_model/pres1/` como proyecto;
2. revalidar el binding del modelo si hizo falta;
3. volver a publicar;
4. revalidar las paginas publicadas.

## 10. Documentar cada cambio junto con su validacion

Cada ajuste importante del frente BI deberia dejar asentado:

- que artefacto se toco: semantic model o reporte;
- si hubo refresh del dataset;
- que consulta DAX o chequeo se uso para validar;
- que guia del repo refleja el nuevo estado.

## Flujo recomendado para cambiar el modelo semantico

1. Editar `definition/` o `model.bim` segun la herramienta elegida.
2. Para cambios acotados, preferir deploy parcial sobre la definicion publicada.
3. Publicar la parte afectada del modelo.
4. Refrescar el dataset.
5. Validar con DAX que la tabla, relacion o medida devuelve lo esperado.
6. Recién despues tocar el reporte publicado.
7. Actualizar esta documentacion y las guias satelite si cambio el consumo.

## Flujo recomendado para cambiar el reporte publicado

1. Identificar el visual o pagina exacta a modificar.
2. Exportar su definicion si hace falta confirmar la estructura vigente.
3. Cambiar el reporte publicado, no asumir que el PBIX local es la ultima verdad.
4. Validar el visual con una de estas vias:
   - export de definicion publicada del visual;
   - `executeQueries` sobre el semantic model;
   - chequeo manual en servicio si aplica.
5. Actualizar la guia funcional correspondiente.

## Checklist minimo antes de publicar una nueva pagina

- La pagina tiene una pregunta analitica clara.
- El dominio esta fijado o separado por bloques.
- La fecha visible sale de `dim_run_modelo[fecha_carga]`.
- El filtro de departamento usa `dim_departamento_master` si la lectura es combinada.
- La medida principal es aditiva o esta calculada como conteo correcto.
- No se suman numeros de riesgo.
- Se validaron datos con DAX o equivalente.
- Se dejo documentada la intencion y el layout.

## Objetos y enfoques que quedan retirados

No deben figurar como flujo vigente en ninguna guia principal:

- `gold`
- `gold_pt`
- referencias a `Modelo_semantico_riesgos_v2` como nombre vigente
- `semantic_model/pres1.pbix` como archivo operativo principal
- slicers temporales de departamento tomados de una fact especifica
- matrices fake armadas con cards
- inferir la ejecucion vigente desde facts en vez de `dim_run_modelo`

- Si cambia el mapa de artefactos locales: actualizar `semantic_model/README.md`.
- Si cambia el layout del reporte combinado: actualizar `semantic_model/GUIA_ARMADO_PBIX_DEPTO_SIC_LLDT.md`.

- Si cambia la puerta de entrada del repo: actualizar `docs/INDICE_DOCUMENTACION.md`.
